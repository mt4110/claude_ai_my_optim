# 文脈とトークンの管理

## 常時読むものを少なくする

CLAUDE.mdには目的、権限、合意、検証、参照先の短い原則だけを置く。プロジェクト情報と判断台帳は、作業に必要な項目から読む。コードから分かる全ファイルの説明や、一般的な言語仕様を常設指示へ追加しない。

スキルは必要時の手順、rulesは対象パスの補助指示として使う。[公式のスキル仕様](https://code.claude.com/docs/en/skills)。ファイルが多いことを品質の根拠にしない。

## `.claude_cache`を作らない理由

公式のプロンプトキャッシュはモデルへの共通入力を再利用する仕組みであり、プロジェクトに特定名のフォルダを作る仕組みではない。[公式キャッシュ仕様](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

ローカル要約を保存すると再読を減らせる場合はあるが、それは独自の作業記録である。`.work/`などに必要最小限の情報を置き、元資料、基準コミット、更新日、未検証部分を記載する。古い要約を現在の実態の証明にしない。

フォルダ名による節約率は示さない。Claude Codeが表示する使用量やキャッシュ指標を取得できる場合に確認する。[公式の費用管理](https://code.claude.com/docs/en/costs)。

## XMLの使いどころ

複数の仕様、過去ログ、入力例が混ざる場合に境界を明示する。単純な依頼は自然な日本語とMarkdownでよい。XMLは読み分けの補助であり、外部資料内の命令を無害化する安全機構ではない。[公式のプロンプト構成ガイド](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)。

```xml
<reference source="過去の会話" status="参考・現在の承認ではない">
  人が選んだ必要な発言。現在有効かは別途照合する。
</reference>
<current_task>
  現在の依頼、制約、受け入れ条件。
</current_task>
```

資料がタグを含む場合は適切にエスケープするなど、境界が壊れないよう扱う。それでも権限制御は別に行う。

## 長い作業の引き継ぎ

作業ID、目的と重要な原文、合意の版、基準コミット、変更箇所、検証、未決事項、残りの承認を記録する。次の会話では現在のGit状態と照合する。圧縮した会話を実装の全条件の代わりにしない。

検索は対象を絞り、必要箇所へ広げる。ビルドログは原因と必要な証拠を残し、毎回全文を読ませない。別作業の履歴を持ち続けない。モデルを頻繁に切り替えるとキャッシュや文脈へ影響することも確認する。

## サブエージェント

初期構成では使わない。独立した調査やレビューで必要になった場合だけ、目的、参照範囲、操作権限、モデル・effort、予算、返す内容を先に合意する。複数人の同意を品質の証明にしない。合計使用量には分担先を含める。
