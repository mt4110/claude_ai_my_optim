# 実装順序と到達点

## 設計版：今回の範囲

設計書、導入用CLAUDE.md、場面別スキル、補助規則、手動統合する設定例、作業・検証・引き継ぎテンプレート、ハーネス仕様・試験ケースを作る。対象案件へ導入せず、公開・pushを行わない。

完成条件は成果物の整合性と、未実装・未検証の境界が明確であること。現場の改善は別の確認が必要である。

追加依頼により、個人用の最小構成を配置するinstall.shは実装した。既存内容の保全、再実行、衝突・リンク・追跡状態・除外の確認を合成プロジェクトで試験した。この実装はハーネスの実装とは別である。[導入スクリプト](INSTALLER.md)を参照。

## 第1段階：監督付きで最小導入

人が対象プロジェクトを選び、既存設定を保全して最小限の指示を統合する。スキル・複数の作業記録・ハーネスの導入は必須にしない。次の代表作業で普通に依頼し、合意・差分・検証と確認負担を照合する。モデルと導入を同時に変更して効果を混ぜない。

終了条件：実際の読み込みと権限、代表作業の結果、人の負担が分かる。実用性がなければ縮小する。ここだけでも役立つなら、無人実行の実装へ自動的に進まない。

## 第2段階：制御アダプターと外部検証

必要性が確認された場合に限り、起動検査、PreToolUseアダプター、保護された条件の検証器を実装する。新しい依存の採用はOS対応、保守、ライセンス、導入負担を確認して決める。

終了条件：異常系を含む制御試験が再現でき、抜け道と残る限界が分かる。フックだけの実装を無人実行可能な状態としない。

## 第3段階：限定した無人実行

人が承認した1作業を、資格情報を持たない隔離環境で実行する。外部の承認ストア、固定の検証ジョブ、差分検証、時間・費用の上限、キャンセルと資源解放を実装する。

終了条件：ハーネスの受け入れ試験と代表作業の証拠がそろい、人が限定運用を承認した。課金・公開・本番操作は個別の承認範囲を維持する。

## 当面追加しないもの

独自のチャットアプリ、汎用MCPサーバー、プラグインの自動配布、全履歴の自動収集、独自キャッシュエンジン、複数エージェントの常設チームは初期範囲に含めない。現場の負担を減らせる根拠が得られてから個別に判断する。
