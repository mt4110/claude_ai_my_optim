# 導入手順

個人用の基本指示は[install.sh](../install.sh)で導入できる。[一回の実行で導入する手順](INSTALLER.md)を参照。既存の指示・設定を保全し、衝突があれば停止する。権限設定やスキルの適用は、このスクリプトの対象に含めない。初期導入は監督付きで使う。

## まず入れるもの

最小構成は、既存のCLAUDE.mdへの方針の統合と、既存資料にないプロジェクト固有条件だけである。普段は自然な会話で依頼する。以下の全手順・全ファイルを初回から必須にしない。[構成ごとの利用境界](USAGE-BOUNDARIES.md)で必要なものを選ぶ。

## 1. 現在の状態を確認する

- VS Code拡張、統合ターミナルのClaude Code、VS CodeのCopilot内のClaudeセッションなど、使っている製品を区別する。本キットの設定はClaude Code向けであり、別製品へ同じファイルを置くだけで効くとは扱わない。
- Claude Codeの版、アカウントで利用できるモデル、会社の利用方針を確認する。モデルやアップデートを自動変更しない。
- 対象のAGENTS.md、CLAUDE.md、親ディレクトリの指示、ユーザー・プロジェクト・ローカル・管理設定を確認する。
- ブランチ、未コミット変更、既存テストの状態を記録する。現在の不具合と今回の回帰を分ける。

拡張とCLIの導入・会話の継続は[公式VS Codeガイド](https://code.claude.com/docs/en/vs-code)を参照。拡張を入れたことと、ターミナルで`claude`を実行できることは別である。

## 2. 小さな導入単位を選ぶ

最初は`kit/CLAUDE.md`から必要な方針を統合する。対象の目的、実際の確認方法、保護対象など、既存資料にない重要な条件だけを`kit/docs/work/PROJECT.md`相当の場所へ整理する。既存資料で足りるなら新設しない。関連コード・設定から分かる情報はClaudeが調べ、人に全項目の入力を要求しない。

`ACTIVE.md`は長い作業を再開するとき、`DECISIONS.md`は訂正や設計判断を会話間で維持するときに追加する。空のテンプレートを揃えることは作業開始条件ではない。未確認のコマンド・権限を推測で埋めて実行しない。

すでにAGENTS.mdが共通指示なら、CLAUDE.mdに`@AGENTS.md`を置く方法もある。ただし大量の文書を重ねて自動インポートしない。本キットの指示と既存の矛盾を先に解消し、同じ規則を複製しない。[公式の読み込み仕様](https://code.claude.com/docs/en/memory)。

CLAUDE.mdの文中にあるパスは参照先であり、すべての自動読み込みを保証するものではない。`@`インポートした内容は開始時に文脈へ入るため、選別して使う。

## 3. スキルと補助指示を統合する

`kit/.claude/skills/`を必要なものから対象の`.claude/skills/`へ統合する。スキル名が既存と衝突していないか確認する。スキルはClaude Code向けであり、すべてのClaude製品へ共通にアップロードできる形式とは扱わない。

- `/align`：目的と変更範囲を合わせる。
- `/implement`：既に承認された作業を実装する。
- `/review-change`：差分と条件を照合する。
- `/handoff`：別の会話へ引き継ぐ。

これらは任意の手動ショートカットであり、通常の会話に必須ではない。自然な依頼はCLAUDE.mdの方針で処理する。スキルを自動起動する設定にはしていない。スキル内には`allowed-tools`やモデルの自動変更を設定していない。

`.claude/rules/`は対象パスの一致を確認して統合する。配置した全規則がすべてのツール経路で強制されるとは扱わない。

## 4. 権限設定をレビューする

[監督付きの設定例](../profiles/supervised.settings.example.json)または[参照中心の設定例](../profiles/observe.settings.example.json)から、必要な項目を選ぶ。設定ファイルを丸ごと上書きしない。管理設定や既存の許可に与える影響を確認する。

監督付き例はManual相当の`default`を明示し、シェル・Web・MCP・Agent等を人の確認へ戻す。ただし、すでにある許可や異なる設定源を含めた実効設定は、このJSONだけでは確定しない。保護対象のEdit/Write拒否は、人がこのキット自体を更新するときに差分を確認して調整する。

サンドボックスは対応環境で動作するか確認する。失敗したときに無制限モードへ自動退避しない。例はBashの制限であり、全ツールの隔離ではない。

監督付き例の`failIfUnavailable`は、隔離が使えない場合の起動失敗を意図する。ネイティブWindowsではこの構成のサンドボックスを使えない。サンドボックス外への再試行禁止は、人が管理する`--settings`や管理設定から与える方法を優先し、既存の除外コマンド・追加ディレクトリ・ネットワーク許可も確認する。設定例を対象リポジトリへ置くだけでは、制限を固定したことにならない。[設定先による公式の違い](https://code.claude.com/docs/en/sandboxing#turn-off-the-retry-with-strict-sandbox-mode)。

設定後に、`/status`、`/permissions`、`/context`で読み込み元・権限・指示を確認する。UIやコマンドが使えない場合は、使用製品・版を確認し、未確認と記録する。[設定の公式説明](https://code.claude.com/docs/en/settings)。

## 5. 非機密の小さな作業で試す

既知の小さな修正を選び、自然な依頼から目的が合っているか、範囲外変更を止めるか、差分と検証を正しく報告するか確認する。既存テストを壊したり本番を触ったりする試験は行わない。

対象プロジェクトの動作確認を行う前に、検証コマンドの副作用・データ・環境を確認する。通常のプロジェクトテストもコードを実行する。

## 6. 導入を戻す必要がある場合

導入前に、既存ファイルと変更した箇所を識別できる記録を残す。戻すときはキット由来の差分だけを提示し、現在のユーザー変更を確認する。削除・破壊的な復元は、対象と影響を示して承認を得る。`reset --hard`や無差別な削除を導入・復旧手順に使わない。

## 無人実行へ進む条件

[ハーネス仕様](HARNESS.md)の外部起動器・承認分離・検証器・隔離を実装し、[受け入れ試験](../harness/CASES.md)を実環境で確認してから、人が許可する。それまではRunAlways等の無制限設定をこのキットで正当化しない。
